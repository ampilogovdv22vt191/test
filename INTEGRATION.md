# Пакетная загрузка для Flask 2.2.5

В Docker запускается один контейнер `file_service`. Веб-процесс создаёт недостающие таблицы в существующем PostgreSQL, восстанавливает состояние очереди и запускает обработчик архивов фоновым потоком. После подготовки он принимает запросы на порту 5000. Обработчик вызывает твою функцию записи в Samba для каждого файла. Именованный том `batch_spool` хранит временные ZIP, чтобы задачи в очереди переживали перезапуск контейнера.

## Запуск примера

Для запуска примера в образе должен быть доступен модуль с твоей функцией записи. В каталоге `file_service` создай `.env` из примера и заполни настройки.

```bash
cp .env.batch.example .env
docker compose up --build -d
docker compose logs -f file_service
```

- `BATCH_DATABASE_URL` указывает на уже существующую базу на другой виртуалке. Учётной записи нужно право создавать таблицы в выбранной схеме. Спецсимволы внутри логина и пароля кодируй как компоненты URL.
- `BATCH_SAVE_FILE` задаёт путь импорта твоей функции, например `server.utils:save_to_samba`. Если она поднимает свой класс исключения для уже существующего файла, укажи его путь в `BATCH_FILE_EXISTS_ERROR`. По умолчанию используется `FileExistsError`.
- `BATCH_AFTER_SAVE` задаёт путь импорта необязательного обработчика после записи, например `server.utils:index_uploaded_file`.
- `APP_PORT` задаёт порт на хосте. По умолчанию API доступен на `http://127.0.0.1:5000` на Docker-хосте. Маршрут `GET /health` проверяет доступность HTTP, включая стартовое создание таблиц.

Контейнер запускает Gunicorn с одним веб-процессом и потоками для HTTP и SSE. Его конфигурация вызывает `start_worker(app)` после импорта Flask. Для запуска через `python run.py` тот же обработчик стартует под `if __name__ == "__main__"`. Вне Docker переменные из `.env` нужно передать в окружение процесса. Для фонового обработчика держи один экземпляр приложения и запускай без автоматического перезагрузчика. Перезапуск контейнера останавливает обработку вместе с Flask. Задачи, которые оставались в очереди, продолжатся после запуска. Незавершённая задача получит `interrupted`.

## Перенос в твой действующий file_service

В примере `server/__init__.py` создаёт глобальный `app`, подключает `CORS(app)` и регистрирует пример ресурса из `server/resources.py` через `Api(app)`. У тебя эти файлы уже содержат рабочие ресурсы, настройки и подключения.

1. Перенеси папку `batch_upload/` в корень рядом с `server/` и `run.py`.
2. В своём `server/__init__.py` вызови `init_batch(app, save_file=save_to_samba)` после создания и настройки глобального `app`. Передай свою функцию из `server/utils.py`. Для своего класса `FileExists` передай также `file_exists_error=FileExists`. Если доступ к старым ресурсам проверяется отдельно, примени те же правила к маршрутам пакетной загрузки, включая SSE.
3. Для запуска через `python run.py` перенеси в свой файл блок старта из примера. `start_worker(app)` готовит БД и запускает поток перед `app.run(..., port=5000)`. Блок `finally` останавливает обработчик. Если запускаешь Gunicorn, используй `gunicorn.conf.py` из примера.
4. Перенеси нужные зависимости из `requirements.txt` и настрой образ и свой Compose по Dockerfile и `docker-compose.yml` примера. У контейнера должен быть постоянный том на `BATCH_WORK_DIR` с правом записи для пользователя приложения. Добавь `BATCH_*` настройки в текущий `.env`.

В примере закреплены Flask 2.2.5 и Werkzeug 2.3.8. Лимиты multipart для пакетной загрузки применяются через класс запроса Flask. Другие маршруты используют настройки лимитов твоего приложения. Архив по умолчанию ограничен 256 МиБ. Если есть обратный прокси, его лимит должен учитывать multipart-обёртку, а для SSE нужна потоковая отдача ответа.

Пример подключения к уже существующему `app` в `server/__init__.py`. Используй имена функции и исключения из своего проекта.

```python
from batch_upload import init_batch
from .utils import FileExists, save_to_samba

init_batch(app, save_file=save_to_samba, file_exists_error=FileExists)
```

Функция вызывается синхронно в фоновом потоке и получает один открытый `BytesIO` на файл. Указатель стоит на первом байте, а в `file.name` лежит путь внутри ZIP, например `docs/report.pdf`. Если твоя функция получает имя отдельным аргументом, передай небольшую обёртку, которая возьмёт его из `file.name`. Возврат из функции означает, что запись завершилась. Исключение `FileExistsError` или переданный `FileExists` даёт статус `exists`. Другие исключения дают `error` с причиной `storage_error`.

В момент вызова доступен контекст приложения Flask, а байтовый поток остаётся открытым до возврата функции. Пакетный API отдаёт список и статусы файлов. Для скачивания используй свою существующую ручку.

Быстрые тесты лимитов Flask, вызова функции сохранения и запуска фонового потока можно выполнить после установки зависимостей командой `python -m unittest discover -s tests -v`. Для этих тестов подключения к PostgreSQL и Samba подменены.

## Куда добавлять свою обработку JSON и файлов

`POST /upload/batch` принимает ZIP в поле `archive` и ставит его в очередь. Воркер читает `data.json` из корня ZIP и выполняет правила ниже. Так фронт получает `202` после сохранения архива, а результат проверок видит в деталях задачи.

| Что нужно сделать | Куда добавить код | Как отразить результат |
|---|---|---|
| Проверить формат всего `data.json` или привести его поля к нужному виду | [`_manifest()`](batch_upload/archive.py) после разбора JSON. Базовая проверка требует массив объектов со строковыми `filename`, `country` и `city`. | При ошибке всего манифеста подними `ArchiveError("Причина")`. Вся задача получит `failed` до записи файлов в Samba. |
| Проверить метаданные или свойства конкретного файла, например обязательный `category` или расширение | [`inspect_zip()`](batch_upload/archive.py) в ветке, где найдено ровно одно совпадение для `filename`. `item` содержит запись JSON, а `matching[0]` — сведения о файле в ZIP. | Чтобы отклонить только один файл, создай его `Entry` с `error="твоя_причина"`. Он появится в деталях со статусом `error`, остальные записи продолжат обработку. |
| Прочитать содержимое файла перед записью | [`Worker._save_file()`](batch_upload/worker.py), где байты уже в `BytesIO` и ещё не переданы в `self.save_file(contents)`. | После чтения для проверки верни указатель в начало через `contents.seek(0)`. |
| Выполнить своё действие после новой записи в Samba | Передай функцию `after_save` в `init_batch()`. | Воркер вызывает её при `status == "uploaded"`, перед `record_file(...)`. |

Например, для обязательного поля `category` у отдельного файла можно изменить создание `Entry` в ветке точного совпадения. Это пример для твоей будущей схемы.

```python
category = item.get("category")
error = "missing_category" if not isinstance(category, str) or not category.strip() else None
result.append(Entry(name, member=matching[0], meta=item, error=error))
```

Метаданные из `Entry.meta` сохраняются в `JobFile.meta` и видны в деталях задачи. `take_file()` передаёт эту запись в `WorkFile.meta`. В `process()` поля файла доступны в словаре `item.meta`. При отсутствии метаданных словарь будет пустым.

Когда функция записи в Samba возвращает строку хеша, воркер добавляет её в `batch_files.meta` под ключом `hash` вместе с итоговым статусом файла. Строка из Samba заменяет значение `hash`, если оно уже было в `data.json`. Хеш доступен в `files[].meta.hash` в ответе `GET /upload/batch/<job_id>` и сохраняется также при `post_save_error`.

## Вызов Elasticsearch из собственного приложения

В приложении из примера добавь `index_uploaded_file` в свой `server/utils.py` и укажи `BATCH_AFTER_SAVE=server.utils:index_uploaded_file` в `.env`. `server/__init__.py` импортирует эту функцию при запуске и передаёт её в `init_batch()`.

При прямом подключении в своём `server/__init__.py` используй вызов ниже после настройки `app`. Пример рассчитан на функцию Samba, которая возвращает строку хеша, и функцию Elasticsearch, которая принимает словарь.

```python
from batch_upload import init_batch
from .utils import FileExists, save_to_samba, write_to_elastic

def index_uploaded_file(item, file_hash):
    write_to_elastic({**item.meta, "hash": file_hash})

init_batch(
    app,
    save_file=save_to_samba,
    file_exists_error=FileExists,
    after_save=index_uploaded_file,
)
```

Если используется стандартный `FileExistsError`, аргумент `file_exists_error` можно опустить. Воркер получает функции через `init_batch()`, поэтому прямой импорт `server.utils` ему не нужен. Если самой `utils.py` нужны настройки Flask, внутри её функций используй `current_app` или явно передавай настройки. Вызовы `save_file` и `after_save` выполняются с контекстом приложения Flask.

Второй аргумент `after_save(item, save_result)` — ровно то, что вернула функция Samba. Если она возвращает кортеж или словарь, извлеки хеш из него в своей обёртке. `item.meta` содержит исходные поля из `data.json`, `item.archive_path` — путь файла. Для статуса `exists` обработчик пропускается. Если `after_save` падает, файл остаётся в Samba, в истории появляется `error` с причиной `post_save_error`, затем воркер продолжает со следующим файлом.

Функция [`save_to_samba()`](demo/samba_writer.py) на стенде считает SHA-256 по тем же байтам, которые записывает, и возвращает хеш после успешного сохранения. Чтобы сохранять хеш в PostgreSQL, возвращай его строкой из `save_to_samba` в своём `server/utils.py`. Если библиотека возвращает составной результат, извлеки из него значение хеша перед возвратом.

Для диагностики сравни `file.name`, размер и SHA-256 байтов, полученных через `file.getvalue()`. Представление `BytesIO` в журнале показывает адрес объекта, а Python может повторно использовать этот адрес для следующего файла. Если вычисляешь хеш через `file.read()`, перед отправкой того же потока вызови `file.seek(0)`. Для пути назначения бери `file.name` или формируй уникальный ключ из фактических данных файла.

## Очередь после перезапуска и хранение истории

Если воркер аварийно остановился, при следующем запуске он помечает активную задачу как `interrupted` и продолжает очередь. Подтверждённые результаты сохраняются. Для файла, который в момент сбоя копировался, результат записи может быть неизвестен. При повторной отправке ZIP готовый объект по тому же ключу учитывается как `exists`.

Воркер проверяет срок хранения при старте и раз в минуту, даже пока идёт запись в хранилище. Через восемь часов после `finished_at` он удаляет завершённую задачу и связанные строки файлов из PostgreSQL. Срок задаётся через `BATCH_RETENTION_HOURS`, окно ленты — через `BATCH_HISTORY_HOURS`. Активные задачи и готовые файлы в хранилище сохраняются. После удаления записи запрос деталей по старому `job_id` возвращает `404`.

Временные ZIP удаляются по завершении задачи или при восстановлении после сбоя. После жёсткой остановки может остаться папка ZIP без записи в БД. Такой остаток можно удалить при остановленном контейнере, сверив папки ZIP с очередью.

## API пакетной загрузки для фронтенда

Используй базовый URL файлового сервиса. Один запрос загрузки создаёт одну задачу. Её `job_id` используется для открытия деталей и отмены.

### `POST /upload/batch` — отправить архив

Отправь один ZIP как `multipart/form-data` с полем `archive`. Для нескольких архивов отправляй отдельный запрос на каждый. Сервис поставит их в очередь.

```js
const form = new FormData();
form.append("archive", file, file.name);
const response = await fetch("/upload/batch", { method: "POST", body: form });
```

В корне ZIP должен быть `data.json` с массивом объектов. Для каждого файла укажи точное имя без папок в `filename` и непустые строки `country` и `city`. Имена сопоставляются с учётом регистра. Дополнительные поля сохраняются в метаданных файла.

```json
[
  {"filename": "report.pdf", "country": "Россия", "city": "Москва"}
]
```

**HTTP 202 Accepted** означает, что сервис принял архив в очередь. Заголовок `Location` содержит URL деталей задачи.

```json
{
  "job_id": "b3338b21-0a78-4a1c-9c74-87fe51d4f6c2",
  "status": "queued"
}
```

| HTTP | Когда возвращается |
|---|---|
| `400` | В поле `archive` нет ровно одного файла с именем или в файле ноль байтов. |
| `413` | Превышен лимит ZIP или multipart-запроса. Лимит самого ZIP по умолчанию 256 МиБ. |
| `503` | Ошибка базы данных загрузок. |

После `202` обнови историю и при необходимости открой задачу по `job_id`. Проверка ZIP и `data.json` идёт в фоне. Например, если в `data.json` отсутствует `city`, задача позже получит `failed`, а поле `error` в деталях укажет файл и причину. Для отображения прогресса передачи ZIP можно использовать `XMLHttpRequest.upload.onprogress`. Прогресс обработки после `202` берётся из счётчиков задачи.

### `GET /upload/batch` — получить историю

Параметр `hours` необязательный, допустимы целые числа от 1 до 168. `GET /upload/batch?hours=8` возвращает все активные задачи и завершённые за последние восемь часов, пока их записи хранятся в истории. Для завершённых задач окно считается от `finished_at`. Без параметра используется настройка сервиса, по умолчанию восемь часов. Список отсортирован по времени создания от новых к старым.

Ответ **HTTP 200 OK** содержит `window_hours` и массив `jobs`.

```json
{
  "window_hours": 8,
  "jobs": [
    {
      "job_id": "b3338b21-0a78-4a1c-9c74-87fe51d4f6c2",
      "archive_name": "reports.zip",
      "status": "uploading",
      "total": 2,
      "processed": 1,
      "uploaded": 1,
      "exists": 0,
      "errors": 0,
      "error": null,
      "created_at": "2026-11-24T07:00:00+00:00",
      "updated_at": "2026-11-24T07:00:05+00:00",
      "finished_at": null
    }
  ]
}
```

`jobs` может быть пустым массивом. Некорректный `hours` даёт `400`. Ошибка базы данных даёт `503`.

| Поля сводки | Что показывать |
|---|---|
| `job_id`, `archive_name` | UUID задачи и имя ZIP в истории. |
| `status` | Текущее состояние из таблицы ниже. |
| `total`, `processed` | Всего строк файлов и сколько уже учтено в прогрессе. Пока `total` равен `null`, показывай индикатор без процента. При `total > 0` используй `processed / total`. |
| `uploaded`, `exists`, `errors` | Сколько файлов загружено, уже существовало или завершилось ошибкой. |
| `error` | Текст ошибки всей задачи или `null`. Показывай его в деталях, например при неверном `data.json`. |
| `created_at`, `updated_at`, `finished_at` | Даты в ISO 8601. До завершения `finished_at` равен `null`. |

| Статус задачи | Что означает |
|---|---|
| `queued` | Архив ждёт своей очереди. |
| `validating` | Сервис проверяет ZIP и `data.json`. |
| `uploading` | Сервис обрабатывает файлы. |
| `cancelling` | Запрошена отмена. Воркер останавливается после уже взятого файла. |
| `done` | Обработка завершилась без ошибок. В числе обработанных могут быть существующие файлы. |
| `done_with_errors` | Обработка завершилась, у отдельных файлов есть ошибки. |
| `failed` | Ошибка всей задачи, например у записи в `data.json` отсутствует обязательное поле. |
| `cancelled` | Задача отменена. |
| `interrupted` | Выполнение прервано остановкой или сбоем обработчика. |

Первые четыре статуса активные, остальные итоговые. Завершение определяй по `status`. У отменённой или прерванной задачи `processed` может быть меньше `total`.

### `GET /upload/batch/<job_id>` — получить детали задачи

Подставь UUID задачи. При **HTTP 200 OK** приходит объект сводки со всеми полями из списка и массивом `files`. `200` означает, что детали получены. Результат загрузки определяется полем `status`, в том числе `failed`. Пока архив ждёт или проверяется, `files` может быть пустым.

Одна строка в массиве `files` выглядит так.

```json
{
  "file_id": "703157ea-d29d-4b52-8eed-b53627be77dd",
  "filename": "report.pdf",
  "archive_path": "docs/report.pdf",
  "size": 1024,
  "meta": {
    "filename": "report.pdf",
    "country": "Россия",
    "city": "Москва",
    "hash": "f144a6907dc4284d1f9fe6a7d9b9ff53c02c1d07ba68f24d413d7ff7f757a782"
  },
  "status": "uploaded",
  "reason": null
}
```

Используй `file_id` как ключ строки. `archive_path` — относительный путь внутри ZIP, `size` — размер файла в байтах. `archive_path`, `size` и `meta` могут быть `null`. В `meta` лежат поля из `data.json`. Когда Samba возвращает строку хеша после записи, сервис сохраняет её в `meta.hash`.

| Статус файла | Что показывать |
|---|---|
| `pending` | Ожидает обработки. |
| `processing` | Обрабатывается. |
| `uploaded` | Загружен. |
| `exists` | Уже есть в хранилище. |
| `error` | Ошибка. Текст для строки выбирай по коду из `reason`. |
| `cancelled` | Отменён. |
| `interrupted` | Обработка прервана. |

| Код `reason` | Текст для пользователя |
|---|---|
| `ambiguous_filename` | В ZIP несколько файлов с таким именем. |
| `duplicate_metadata` | В `data.json` несколько записей для этого имени. |
| `file_not_found_in_archive` | Файл из `data.json` отсутствует в ZIP. |
| `no_metadata` | Для файла нет записи в `data.json`. |
| `file_too_large` | Файл превышает допустимый размер. |
| `invalid_zip_member` | Содержимое файла повреждено или использует неподдерживаемое сжатие. |
| `storage_error` | Не удалось записать файл в Samba. |
| `post_save_error` | Файл записан в Samba, дальнейшая обработка завершилась ошибкой. Хеш сохранён, если его вернула Samba. |
| `job_cancelled` | Обработка файла отменена вместе с задачей. |
| `worker_interrupted` | Обработка файла прервана при остановке воркера. |
| `job_failed` | Обработка файла остановлена из-за ошибки всей задачи. |

`reason` может быть `null`. Если сервис вернул новый код, покажи общий текст ошибки и сам код.

`404` с `{"error":"Загрузка не найдена"}` означает, что задача отсутствует или её история уже удалена. В этом случае обнови список и закрой детали. Ошибка базы данных даёт `503`.

### `POST /upload/batch/<job_id>/cancel` — отменить задачу

Достаточно отправить `POST` по UUID задачи, тело запроса пустое. Показывай кнопку отмены для `queued`, `validating` и `uploading`.

| Состояние при запросе | HTTP | Тело ответа |
|---|---|---|
| `queued` или уже `cancelled` | `200` | `{"job_id":"…","status":"cancelled"}` |
| `validating`, `uploading` или уже `cancelling` | `202` | `{"job_id":"…","status":"cancelling"}` |
| `done`, `done_with_errors`, `failed` или `interrupted` | `409` | `{"error":"Загрузка уже завершена","status":"…"}` содержит текущий статус задачи. |
| Задача отсутствует или удалена | `404` | `{"error":"Загрузка не найдена"}` |
| Ошибка базы данных | `503` | `{"error":"База данных загрузок временно недоступна"}` |

При `202` покажи «Отменяется» и дождись `cancelled` в деталях. Если файл уже взят в работу, воркер завершит его обработку. Оставшиеся строки файлов получат `cancelled`, а записанные файлы останутся в Samba. При `409` перечитай детали, поскольку задача могла завершиться между отображением кнопки и кликом.

### `GET /upload/events` — отслеживать изменения

Подключи один `EventSource` на открытый экран или модальное окно истории. Ответ имеет тип `text/event-stream`. Событие `sync` приходит при подключении, в том числе повторном, и при изменении ревизии.

```text
event: sync
data: {"revision": "42"}

```

`revision` — строка. `sync` сообщает, что нужно заново получить список задач и детали открытой задачи. Одно событие может охватывать несколько изменений. При стандартных настройках сервер примерно каждые 15 секунд отправляет служебный комментарий `: heartbeat`. При потере соединения браузер переподключается, а первое `sync` запускает обновление данных.

### Как связать запросы на экране

1. При открытии истории загрузи `GET /upload/batch` и подпишись на `/upload/events`.
2. При выборе строки запрашивай `GET /upload/batch/<job_id>` сразу. Для последующих обновлений держи UUID выбранной задачи.
3. На `sync` перечитывай список и выбранные детали. При нескольких событиях во время запроса достаточно одного повторного обновления после ответа. Если пользователь сменил выбор, покажи детали для актуального UUID.
4. После отправки архива или отмены обнови данные сразу. При закрытии окна закрой `EventSource` и отмени незавершённые запросы на чтение.

Обработчики HTTP-ошибок возвращают текст в JSON-поле `error`. Если тело ответа пришло в другом формате, используй HTTP-код для общего сообщения. Для архивов со статусом `failed` показывай `error` из успешного ответа с деталями.

Пример подписки и обновления истории для браузера. `renderJob(null)` закрывает или очищает панель деталей.

```js
function watchUploads(getSelectedJobId, renderJobs, renderJob, showError) {
  const cancel = new AbortController();
  const events = new EventSource("/upload/events");
  let pending = false;
  let running = false;

  async function get(url, allowMissing = false) {
    const response = await fetch(url, { signal: cancel.signal, cache: "no-store" });
    if (allowMissing && response.status === 404) return null;
    if (!response.ok) {
      const error = await response.json().catch(() => ({}));
      throw new Error(error?.error ?? `HTTP ${response.status}`);
    }
    return response.json();
  }

  async function refresh() {
    pending = true;
    if (running) return;
    running = true;
    while (pending && !cancel.signal.aborted) {
      pending = false;
      const id = getSelectedJobId();
      try {
        const [list, job] = await Promise.all([
          get("/upload/batch"),
          id ? get(`/upload/batch/${encodeURIComponent(id)}`, true) : null,
        ]);
        renderJobs(list.jobs);
        if (id === getSelectedJobId()) renderJob(job);
      } catch (error) {
        if (error.name !== "AbortError") showError(error);
      }
    }
    running = false;
  }

  events.addEventListener("sync", refresh);
  void refresh();
  return {
    refresh,
    close() {
      events.close();
      cancel.abort();
    },
  };
}
```

При подключении через прокси сохрани потоковую отдачу для `/upload/events` и выставь таймаут чтения выше 15 секунд. Лимит размера запроса у прокси должен учитывать максимальный размер ZIP и multipart-обёртку. Если Flask уже защищён аутентификацией, используй действующие правила доступа и для пакетных маршрутов и SSE.
